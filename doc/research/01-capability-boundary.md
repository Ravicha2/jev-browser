## 1. The capability boundary

Cloudflare published the cleanest formal statement of it. Their July 2026 taxonomy splits automated traffic three ways and defines **Agent** as "automated behavior that is acting, usually in real time, on a person's behalf, to get something done right now… includes chat fetch bots (e.g., ChatGPT-User) and **browser-use agents (e.g., Gemini or Claude driving Chrome)**", against **Search** as "any behavior that collects or indexes your content, so it can answer questions about it later." `[P]` https://blog.cloudflare.com/content-independence-day-ai-options/

### 1.1 What HTTP-only fetch structurally cannot do

- **Authenticated session state.** `[M]` With no cookie, `github.com/settings/profile` returns `302 → /login` with the login page as its body; `api.github.com/user` and the Gmail messages endpoint both return `401`. Content behind SSO or MFA is unreachable by fetch by construction, not by difficulty. `[P]` The deep-research roadmap paper names the same three walls: API-driven pipelines "can struggle with deeply nested, client-side JavaScript–rendered content, interactive components, or **authentication barriers**." https://arxiv.org/html/2506.18096v2
- **Canvas and JavaScript-rendered interfaces.** `[M]` Google Maps over plain HTTP: **190,809 bytes of HTML, 131 characters of visible text**, reading "Google Maps. When you have eliminated the JavaScript, whatever remains must be an empty page." No extraction layer fixes that; the content is not in the response.
- **State mutation versus reading.** Halluminate's Web Bench (2,454 tasks, 452 real sites): SOTA agents reach **46.6% on write-heavy tasks** (login, form fill, file download) but **over 75% on read-heavy tasks**, with "infrastructure issues… proxies, captcha, and login/authentication" named as the blocker. `[P]` https://www.halluminate.ai/blog/benchmark
- **Closed shadow roots and frames.** Browser Use: "Playwright adds assumptions, such as locators that cannot see closed shadow roots. CDP can inspect those roots directly," with a worked nested shadow-root case where the button is on screen but absent from the extracted state. `[V]` https://browser-use.com/posts/bitter-lesson-browser-agents
- **Geo and session-dependent redirects.** `[M]` `airbnb.com/s/San-Francisco--CA/homes` over plain HTTP returned an **863-byte redirect stub** to a country domain, not results.
- **Enterprise auth-gated multi-app workflows.** Emergence's EEBD-v1 exists because "accessing enterprise systems requires valid, often dynamically managed, credentials and robust authentication mechanisms (SSO, MFA), posing a significant initial hurdle." `[V]` https://www.emergence.ai/blog/frxkjpgyojmjcjtglnso37b1lnnwho

### 1.2 The strongest single finding: the search camp's own crawlers do not execute JavaScript

Better evidence than any fetch test. Vercel and MERJ analysed real crawler traffic on Vercel's network (GPTBot 569M requests, Claude 370M), validated on non-Next.js stacks. Verbatim: "**none of the major AI crawlers currently render JavaScript**", naming OpenAI (OAI-SearchBot, ChatGPT-User, GPTBot), Anthropic (ClaudeBot), Meta (Meta-ExternalAgent), ByteDance (Bytespider), and Perplexity (PerplexityBot). The detail that settles it: ChatGPT fetches JavaScript files in 11.50% of requests and Claude in 23.84%, but "they don't execute them. They can't read client-side rendered content." Common Crawl (CCBot) does not render. Only exceptions: Gemini, riding Googlebot infrastructure, and AppleBot. `[P]` https://vercel.com/blog/the-rise-of-the-ai-crawler

Mechanism confirmed by Google: "the app shell model where the initial HTML does not contain the actual content", and "Other search engines may choose to ignore JavaScript and won't see JavaScript-generated content." `[P]` https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics

Independent corroboration. Glenn Gabe tested a fully client-rendered site by asking each platform to return the first and last paragraphs of specific URLs. ChatGPT, Perplexity, and Claude each failed and said so explicitly; one reported it "could not read the content of the page because it relied on JavaScript-based rendering." Non-JS control pages worked on all three; Google and Bing were unaffected. `[S]` https://www.gsqi.com/marketing-blog/ai-search-javascript-rendering/

### 1.3 The counterweight: the browser is necessary but not sufficient

Four structural limits on the browser side. These undercut any claim that the browser is the general answer.

- **The accessibility tree is a subset of the DOM, not a superset.** Microsoft Edge DevTools docs: "The Accessibility Tree is a subset of the DOM tree, which contains elements that are relevant and useful for displaying the contents of a page in a screen reader." An agent reading the accessibility tree reads a filtered view. `[P]` https://learn.microsoft.com/en-us/microsoft-edge/devtools/accessibility/test-accessibility-tree
- **That filtering produces documented agent failures.** Elements visually present but carrying `aria-hidden="true"` are excluded from AI snapshots: "This causes visually important elements to be excluded from AI snapshots." `[P/S]` https://github.com/microsoft/playwright/issues/37204
- **Closed shadow roots stay unreachable even for Playwright**, which pierces open roots automatically but has no supported path into closed ones; open feature request since 2023. `[P/S]` https://github.com/microsoft/playwright/issues/23047 This qualifies the Browser Use CDP argument above: CDP can inspect closed roots, Playwright-the-driver cannot.
- **Virtualized lists put only visible rows in the DOM.** TanStack: virtualization "keeps the DOM small by only rendering the items that are visible in the scroll viewport plus a small overscan buffer." A 50,000-row grid returns the shell plus a handful of rows. `[P]` https://tanstack.com/table/latest/docs/framework/react/guide/virtualization

Net effect: between aria-hidden filtering, the tree being a DOM subset, closed shadow roots, and virtualization, real classes of content are unreadable by any current agent. That is a reason to prefer structured endpoints where they exist, not an argument for the browser.

### 1.4 Canvas, from Google's own guidance

Verbatim: "Regular `<canvas>` content is not exposed to browser features such as screen readers, indexing, translation tools, accessibility assistive tools, find-in-page, print, etc." Google's proposed remedy, HTML-in-Canvas with `layoutsubtree` and `drawElementImage`, exists precisely because canvas pixels are invisible to the tree. `[P]` https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/visual-design/expose-canvas-content-to-browser-features.md

Also from Google: "Google Search does not interact with your page", so scrolling and clicking load nothing for it, and indexable infinite scroll requires the site to "update the displayed URL using the History API", meaning state must be encoded in the URL to be reachable at all. `[P]` https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading

### 1.5 A/B variants are cookie-scoped, so a fetch cannot know which page it saw

Cloudflare's same-URL A/B testing docs assign the group with `Math.random()`, rewrite the path server-side to `/control` or `/test`, and persist with `Set-Cookie: myExampleABTest=<group>`. A cookie-less fetch gets a coin-flip variant with no way to know which one it saw, or to ask for the other. `[P]` https://developers.cloudflare.com/rules/snippets/examples/ab-testing-same-url/ The cleanest concrete instance of "the page's own state, not its HTML source, is the content."

## 2. Published failure evidence, and where search plus fetch wins

**The decisive controlled ablation.** "Beyond Browsing: API-Based Web Agents" (CMU, arXiv 2410.16464) ran the same WebArena tasks with three agents: **Browsing 14.8%, API-only 29.2%, Hybrid 38.9%**, a **24.0 point absolute gain** over browsing alone and SOTA among task-agnostic agents. Verbatim: "when APIs are available, they present an attractive alternative to relying on web browsing alone." `[P]` https://arxiv.org/abs/2410.16464

**OpenAI's own BrowseComp table is the sharpest single contrast.** GPT-4o **0.6%**; GPT-4o **with browsing 1.9%**; GPT-4.5 0.9%; **OpenAI o1 with no browsing 9.9%**; Deep Research **51.5%**. OpenAI's own reading: "browsing alone is not sufficient, models must also be capable of reasoning strategically." Human trainers solved 29.2%. `[P]` https://openai.com/index/browsecomp/

**Browser-agent benchmark reality check:**

- **Online-Mind2Web** ("An Illusion of Progress?", COLM 2025, 300 tasks across 136 live sites): Operator **61.3%**, Claude Computer Use 3.7 **56.3%**, everything else around **30%**; "suggesting **over-optimism in previously reported results**"; many agents "do not outperform the simple SeeAct agent released in early 2024." `[P]` https://arxiv.org/abs/2504.01382
- **WebVoyager audited** (Emergence, arXiv 2603.29020, March 2026): re-running Operator yields **68.6%, "substantially lower than the 87% previously reported by OpenAI"**; 11 methodological shortcomings found; inter-annotator agreement 95.9%. `[P]` https://arxiv.org/abs/2603.29020
- **OSWorld-Human** (arXiv 2506.16042): systems are "practically unusable due to **extremely high end-to-end latency (e.g., tens of minutes) for tasks that typically take humans just a few minutes**"; each successive step can take **3x longer** than early steps; best agents take **2.7 to 4.3x more steps than necessary**. `[P]` https://arxiv.org/abs/2506.16042
- **OSWorld 2.0**: best agent **20.6% binary completion** (54.8% partial) at 500 steps and **around 318 tool calls** versus about 30 in OSWorld 1.0; failure diagnosis: agents "lose track of constraints, miss information that arrives mid-task, guess rather than ask the user, and skip verification." `[P/S]` https://osworld-v2.xlang.ai **Flagged: Steel's aggregator lists 52 to 78% for the same benchmark. Irreconcilable, different metrics and harnesses; prefer the paper.**
- **BrowserArena** (arXiv 2510.02418) step-level annotation found three consistent failure modes: **captcha resolution, pop-up banner removal, and direct navigation to URLs**, the last a pure "the model cannot do the trivial thing" finding. `[P]` https://arxiv.org/abs/2510.02418
- **Reliability is the admission from inside the camp.** Browser Use, November 2025: "We're already at **under 2¢ per task and 4x faster** than a year ago. The cost and speed problems are largely solved. **But… reliability is still the biggest pain point preventing widespread adoption.**" Their own 100-hard-task benchmark: best 80.0%, and that run cost $580.87. `[V]` https://browser-use.com/posts/one-year-of-progress

**Failure-mode taxonomy, with an unresolved contradiction that should not be papered over:**

- ACL 2026 (Aghzal et al., pp. 32157 to 32180): "**low-level execution remains the dominant bottleneck**… improving perceptual grounding and adaptive control, not only high-level reasoning, is critical." `[P]` https://aclanthology.org/2026.acl-long.1483/
- IBM, "From Grounding to Planning": "**Contrary to prevalent assumptions… grounding is not a significant bottleneck**. Instead, the primary challenge lies in the **planning** component." `[P]` https://research.ibm.com/publications/from-grounding-to-planning-benchmarking-bottlenecks-in-web-agents
- These directly contradict. Both are recorded; neither is settled.

**Cost of failure.** Online-Mind2Web finds "failed tasks involve **nearly twice as many steps** as successful ones." `[P]` arXiv 2504.01382 At 90% per-step accuracy a 10-step task clears only about 35% of the time. `[S]` https://www.testmuai.com/blog/state-of-ai-browser-agents-2026/ (vendor, but the arithmetic is checkable).

## 3. Deterministic versus LLM-planned control flow

**Microsoft and Playwright, determinism as the design thesis.** Playwright MCP's README: "Uses Playwright's accessibility tree, **not pixel-based input**… **Deterministic tool application. Avoids ambiguity common with screenshot-based approaches.**" The tool descriptions encode it in the prompt: `browser_snapshot` is "this is better than screenshot"; `browser_take_screenshot` warns "**You can't perform actions based on the screenshot, use browser_snapshot for actions**." `[P]` https://github.com/microsoft/playwright-mcp

**Microsoft's own concession against their MCP.** The same README says Claude-style CLI plus skills are preferred because they "**avoid loading large tool schemas and verbose accessibility trees into the model context**," scoping MCP to loops "where maintaining continuous browser context **outweighs token cost concerns**." `[P]` same URL. Microsoft publishes no numeric token-per-snapshot table; circulating figures (200 to 400 versus 3,000 to 5,000 tokens) are `[S]` third-party and unverified.

**Anthropic assigns control flow by predictability, and routes around the browser when it can.** "**Workflows** are systems where LLMs and tools are orchestrated through **predefined code paths**. **Agents**… **dynamically direct their own processes**." Their browser-use docs give the tiebreak: "Choose browser use when the task stays inside webpages **and means acting on them**… **For reading pages you can point Claude to, or finding sources on the web, the web fetch tool and web search tool are lighter. They're server tools that the API runs for you, with no browser to operate.**" `[P]` https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool and https://www.anthropic.com/engineering/building-effective-agents

**The hybrid vendors have converged on "compile the trajectory".** This is the most important recent development for this effort, because it is jev-browser's own thesis arrived at independently.

- **Stagehand**: "**Scripts gives you precision. Agents give you flexibility. Stagehand gives you both**." Its comparison table concedes the fully-agentic rung is not "fast, cheap, and predictable" (that row is Yes/Yes/**No**). `[V]` https://browserbase.com/stagehand
- **Stagehand caching**: "**the winning move is the opposite: avoid reasoning entirely**… On a cache hit, the goal is simple: **avoid the LLM and execute deterministically**," with the caveat "**A wrong cached click is worse than a slow click.**" `[V]` https://browserbase.com/blog/stagehand-caching
- **Skyvern**: "**records the actions an AI run takes and generates executable code from them. Subsequent runs execute the cached code directly, skipping LLM inference and screenshot analysis. Faster, cheaper, deterministic**," with agent fallback when the page changes. `[V]` https://skyvern.com/docs/developers/features/code-caching.md
- **Notte**: "combines AI agents with traditional scripting… letting you **script deterministic parts and use AI only when needed, cutting costs by 50%+**," through an `AgentFallback` wrapper. `[V]` https://github.com/nottelabs/notte
- **Anchor Browser**: "AI Agents to **plan** and deploy **deterministic browser tasks** — Only reverting to AI in runtime when it is actually required." `[V]` https://anchorbrowser.io (their 12x, 80x, and 23x claims are unreplicated marketing)
- **Browserbase's decision rule, stated outright**: "**If a wrong click costs money or fails an audit, you want a script. If you can't enumerate the sites, layouts, or workflows ahead of time, scripting becomes a losing fight and you want an agent.**" `[V]` https://docs.browserbase.com/use-cases/agents
- **RPA incumbents on why determinism matters.** UiPath: "**sometimes determinism is good, meaning it works the same way every time. And if it fails, it fails the same way every time.**" and "**Agents are non-deterministic by nature.**" `[S]` https://diginomica.com/uipath-explains-hybrid-automation-architecture-why-agents-need-workflows-not-other-way-around (disclosed UiPath partnership). Automation Anywhere: "RPA is excellent at handling repetitive, deterministic tasks." `[V]` https://www.automationanywhere.com/company/press-room/automation-anywhere-takes-step-towards-artificial-general-intelligence-work
- **Academic versions**: AgentRR record-and-replay (arXiv 2505.17716); LOOP Skill Engine claims replay "**reduces monthly token consumption by 93.3% to 99.98% and cuts execution latency by 8.7x while eliminating output non-determinism**" (arXiv 2605.14237). `[P]`

**The opposing camp, at full strength.** Stagehand: "**Selectors break. Natural language doesn't.**" Browserbase: "**Most of the web has no API**… Create **one reusable Agent** instead of maintaining hundreds of scripts." `[V]` And Browser Use's September 2026 "Bitter Lesson" rejects predefined action and state spaces entirely in favour of model-written raw CDP code, reporting Hermes replaced 12 browser tools with `browser_exec` and cut **mean token use 60% (Opus 4.8) and 66% (Kimi K3)** at 18 of 18 runs. `[V]` https://browser-use.com/posts/bitter-lesson-browser-agents

**The synthesis that is load-bearing.** Browser Use's answer is model-written code, not model-per-step decisions, which is a determinism-adjacent position. The striking 2025 to 2026 fact is that **nearly every vendor selling LLM browser control now scopes the LLM to locating and planning and hands execution back to deterministic code** through caching, compilation, plan-then-deploy, or script-first-with-fallback. Steel.dev is the conspicuous abstainer, selling only browser infrastructure and leaving AI planning to the customer.

**One negative finding, now confirmed and therefore dropped.** The widely quoted Stagehand positioning "AI where it matters, code where it counts" **does not appear on any of Stagehand's three properties**: browserbase.com/stagehand, stagehand.dev, and docs.stagehand.dev all return zero matches. Do not attribute it to them, and do not carry it in the brief at all. The verified tagline is "Scripts gives you precision. Agents give you flexibility. Stagehand gives you both.", and the docs' own framing of the choice is "You're stuck between two bad options: Too brittle... Too agentic." **Scope of the negative:** absence on the three properties inspected, not a global web search (WebSearch is non-functional in this environment), so a third-party post could still be the phrase's origin. The operational conclusion is the same either way: it is not Stagehand's line, so cite the verified tagline instead. `[S, systematic negative check, re-confirmed 2026-09-22]`

## 4. The economics

**Browser-agent side:**

- **Cheapest published per-task figure.** Browser Use, one year: accuracy 71.8% to 82.0%, task time **123s to 33.4s**, cost **39.2¢ to 1.9¢ per task**. Verbatim: "It now costs less than 2 cents to complete a simple browsing task." `[V]` https://browser-use.com/posts/one-year-of-progress
- **The same vendor's hard-task benchmark costs 300x that**: about **$10 per 100-task run** on the basic plan, and **$580.87 per 100-task run ($5.81 per task) with their top model at 80.0% accuracy and 6m53s per task**. A single 100-task run takes about **3 hours**. Throughput: bu-ultra about **14 tasks per hour**, GPT-5 about **6 tasks per hour**. `[V]` https://browser-use.com/posts/ai-browser-agent-benchmark
- **Latency, DOM agent versus vision computer-use, same benchmark** (OnlineMind2Web average seconds per task): Browser Use **68s**; Gemini 2.5 CU **225s**; Claude Sonnet 4.5 **285s**; Claude Sonnet 4 **295s**; OpenAI CUA **330s**. About 3s per step; each screenshot adds about **0.8s** of encoder latency; output tokens cost about **215x more time per unit** than input. `[V]` https://browser-use.com/posts/speed-matters
- **The vision tax, from Anthropic's own docs**: images cost `ceil(width/28) * ceil(height/28)` visual tokens; caps are **1,568** tokens (standard, 1568px long edge) versus **4,784** (Claude 4.7 and later, 2576px). A 1920x1080 screenshot is **1,560 tokens standard or 2,691 high-res**. For computer-use and browser-use toolsets the API **rejects** oversized images rather than downscaling, so the application must resize. `[P]` https://docs.claude.com/en/docs/build-with-claude/vision
- **Infrastructure**: Browserbase **$0.10 to $0.12 per browser-hour**; Browser Use Cloud **$0.02 per browser-hour** plus a **20% service fee** on model cost; residential proxies $5 to $12 per GB. `[V]` https://www.browserbase.com/pricing, https://browser-use.com/pricing
- **Concurrency is metered and sold**, so it is a real cost driver: Browserbase caps **3, 25, 100, 250+** concurrent browsers by plan with a **15-minute session cap** on free; Browser Use Cloud gates concurrency by lifetime spend, **10 concurrent at $0 rising to 1,000 at $25,000**. `[V]` same URLs
- **Long-horizon completed-task cost** (analysis, OSWorld 2.0 arithmetic): about **$29.60 per completed task** for a flagship (roughly 244K output tokens per attempt at 20.6% completion) versus about **$8.70** for a token-thrifty model. The authors flag these as **output-token floors only**, since input tokens, "which include repeated screenshots in computer-use loops, typically dominate the real bill." `[S]` https://o-mega.ai/articles/the-2025-2026-guide-to-ai-computer-use-benchmarks-and-top-ai-agents

**Search plus fetch side:**

- **Unit prices**: Tavily **$0.008 per credit** (basic search 1 credit; basic extract 1 credit **per 5 URLs**; 180ms p50); Exa **$7 per 1k searches**, **$1 per 1k pages**; Brave **$5 per 1k requests**; OpenAI web search **$10 per 1k calls**; Browserbase Search **$7 per 1k**, Fetch **$1 per 1k**; Gemini grounding **$14 per 1k requests** after 5,000 free per month. `[V]` https://docs.tavily.com/documentation/api-credits, https://exa.ai/pricing, https://brave.com/search/api/, https://www.browserbase.com/pricing
- **Deep research (pure search plus fetch) per query**: Gemini Deep Research **$1 to $3 per task standard, $3 to $7 Max**, with about **80 search queries per task standard and about 160 Max**, so **$1.12 to $2.24 in search fees alone, "more than the inference cost"**; about 250K input and 60K output tokens standard, about 900K input Max; 5 to 15 minutes per task. OpenAI o3-deep-research about **$1.45 per task**; o4-mini-deep-research about **$0.41 per task**. `[S, derived]` https://tokencost.app/blog/gemini-deep-research-agent-cost
- **Search-API quality spread on BrowseComp** (6 APIs, GPT-5.4 harness, at most 20 tool calls per question, July 2026): **about 19% to about 58%**; OpenAI web search **57.7%**, Parallel **51%**, Brave **38.3%**. Independently, **Artificial Analysis's Search Index** (20 products, 10 providers, fixed harness, latest data 8 September 2026) is the non-vendor reference and publishes cost per task and time per task. `[V/S]` https://parallel.ai/articles/best-ai-search-for-agents, https://artificialanalysis.ai/agents/search-api
- **Deep research session cost, provider view**: "a single user session can cost the provider **$5 to $30 in API fees**." `[S]` https://zylos.ai/research/2026-04-21-deep-research-agent-architectures/ treat as indicative.

**A measured cost gap.** September 2026 benchmark, 1 vCPU and 2 GB: Shopify's public `/products.json` returned in 0.14 to 0.23s against 7.04s for headless Chromium rendering the equivalent collection page, roughly 30 to 50x slower, at 146 MB peak child RSS for one page, plus 0.53s launch before navigation. Bonus trap: `wait_until='networkidle'` timed out at 30 seconds and never completed on a live storefront because analytics, personalisation, and chat XHRs keep the network busy indefinitely. The same post names where headless genuinely wins: infinite-scroll grids with no backing API, client-side-rendered SPAs, and interactions requiring clicking. `[V, single machine, one store, directionally solid rather than a survey]` https://fetchsmith.com/blog/http-only-vs-headless-browser-scraping-cost

**The asymmetry, stated plainly.** Search fan-out is priced per *call* and is parallel by default; no vendor publishes a concurrent-searches paid ceiling the way browser sessions are capped. A browser agent is **stateful and serialized**, priced per session-hour plus model tokens, and capped by concurrency tiers. Eighty parallel search queries cost about $1.12; the equivalent browser work is minutes of wall clock on a metered session. Counterpoint worth citing: one measured fan-out study found 4 agents burned **29,000 tokens where 1 agent used 10,000** (about 3x coordination glue), with orchestration overhead of **50 to 200ms per step** and a 1.6 to 2.2x latency gain at 1.7 to 2.6x token cost. `[S]` https://tianpan.co/blog/2026/05/02/parallelism-trap-agentic-pipelines-fan-out-latency

## 5. What contradicts the premise, stated plainly

**a. On ordinary discovery tasks, search plus fetch wins, and not marginally.** A controlled result, not an opinion: same WebArena tasks, API-only agent **29.2%** against browsing agent **14.8%**, roughly double. `[P]` arXiv 2410.16464. And on BrowseComp, **o1 with no browsing at all (9.9%) beats GPT-4o with browsing (1.9%) by about 5x**; a search-plus-fetch deep-research system beats browsing GPT-4o by about 27x. `[P]` https://openai.com/index/browsecomp/ The top of Mind2Web 2 is **OpenAI Deep Research at 50 to 70% of human performance at half the time**, a search-and-read system. `[P]` https://osu-nlp-group.github.io/Mind2Web-2/ **A browser agent is the wrong tool for "find and read information," and the best available evidence says so directly.**

**b. The cost argument for search plus fetch has largely evaporated on simple tasks.** At **1.9¢ and 33.4 seconds per simple browsing task** `[V]` browser-use, a browser agent is not obviously more expensive than a deep-research query at **$0.41 to $3.00** `[S]`. Cost now favours browser agents on simple tasks and search plus fetch only on high-fan-out reads. The honest cost distinction is **fan-out breadth**, not unit price.

**c. Browser agents may beat search plus fetch precisely where search plus fetch is weakest: genuinely novel facts.** LiveBrowseComp (arXiv 2605.28721, May 2026) is the strongest evidence against search plus fetch's competence. Findings: agents answer **up to 44.5% of BrowseComp questions with no tools at all**; **more than half of their search queries come from internally generated hypotheses rather than retrieved leads** ("The loop is model-led, not evidence-led"); **removing answer-supporting evidence makes search-augmented agents perform WORSE than closed-book baselines**; and on 90-day-fresh questions **all agents fall below 2% closed-book with search-augmented scores down 25 to 40 points**, inverting prior rankings. `[P]` https://arxiv.org/abs/2605.28721
  **Caveat to carry:** this shows that search-only agents are weaker than their scores suggest. It does **not** show that a browser agent does better on the same task; **no head-to-head browser-versus-search run on LiveBrowseComp was found.** Treat "browsing is the answer to freshness" as a hypothesis, not a result.

**d. Benchmarks inflate in both directions.** WebVoyager was audited down from 87% to **68.6%** for Operator `[P]` 2603.29020; Online-Mind2Web calls prior results "over-optimism" `[P]` 2504.01382; a rigor paper finds benchmark task and reward issues "can lead to under- or overestimation of agents' performance by **up to 100% in relative terms**" `[P]` arXiv 2507.02825. Notably, Online-Mind2Web's authors **had to prompt agents not to use Google Search "to prevent shortcuts"** and Web Bench **penalizes agents for using external search**; both are admissions that the search path inflates scores on benchmark tasks. `[P]`

**e. Search plus fetch has a structural permission advantage that no amount of engineering fixes.** From **15 September 2026**, Cloudflare's stated default for newly onboarding domains is that "the categories of **Training** and **Agent** will be blocked by default **on the pages that display ads**, while **Search will remain allowed by default**", because "Search is the behavior that most naturally funnels back visitors." `[P]` https://blog.cloudflare.com/content-independence-day-ai-options/ **Correction applied:** Cloudflare's later post refines the Training half, and the brief should not rest on the July wording alone. The current preset is Training = **"Disallow AI Training"**, which is *not* a flat block: "Accountable mixed-use crawlers remain allowed for search. Every other training crawler is blocked." Agent stays **"Block on pages with ads"**, so the half that matters here is unchanged. `[P]` https://blog.cloudflare.com/accountable-mixed-use-ai-crawlers Cloudflare's pay-per-crawl returns **402 Payment Required** to crawlers that do not present payment intent. `[P]` https://blog.cloudflare.com/introducing-pay-per-crawl/ A browser agent is, by Cloudflare's own definition, in the category that gets blocked first. This is a regulatory and policy advantage for search plus fetch independent of capability.

**f. Cloudflare's permission scale, with numbers.** Cloudflare told WIRED it blocked 416 billion AI bot requests since 1 July 2025. The same piece: Google sees 3.2x more pages than OpenAI, 4.6x more than Microsoft, and 4.8x more than Anthropic or Meta. `[S]` https://www.wired.com/story/big-interview-event-matthew-prince-cloudflare/ Cloudflare: "less than 1% of Cloudflare sites choose to block Search bots" but "17% of sites choose to enable some mechanism to block training", and "a robots.txt directive alone cannot solve this problem… it cannot identify who is crawling, determine why they are crawling, or stop a crawler that ignores it." `[P]` https://blog.cloudflare.com/accountable-mixed-use-ai-crawlers llms.txt appears on only 2.13% of desktop and 2.10% of mobile sites (324,184 valid files), and about 40% of those are auto-generated by All in One SEO, "so we cannot be sure this is always a conscious act." Web Almanac 2025 SEO chapter, published 15 January 2026. `[P]` https://almanac.httparchive.org/en/2025/seo By contrast 85% of sites return a valid 200 for robots.txt. Machine-readable permission is standard; machine-readable purpose declaration is not.

**g. One claim that cuts back against the browser camp.** Google now requires JavaScript to serve Search results (from mid-January 2025), widely read as targeting scrapers that do not execute JavaScript. Reported figure: fewer than 0.1% of searches came from people with JavaScript disabled. `[S]` https://serpapi.com/blog/google-now-requires-javascript/ **Caveat:** the 0.1% figure traces to a TechCrunch piece that 404s; treat as secondhand. Separately, Google has deprecated dynamic rendering as "a workaround and not a recommended solution." `[P]` https://developers.google.com/search/docs/crawling-indexing/javascript/dynamic-rendering

**h. Where the reverse case is strongest.** Google's own advice is the tidiest citation that the fetchable subset is the intended one: "Keep in mind that server-side or pre-rendering is still a great idea because it makes your website faster for users and crawlers, and not all bots can run JavaScript." `[P]` https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics Plus: WordPress runs about 40.2% of all websites, with 31.5% using no monitored CMS. Snippet-sourced, the W3Techs table did not render; mark accordingly. https://w3techs.com/technologies/overview/content_management

## 7. Gaps, unverified items, and corrections

- **No head-to-head browser-versus-search evaluation on fresh-fact benchmarks** (LiveBrowseComp or equivalent). This is the single biggest hole and it is the crux of the question.
- **All vendor performance deltas are self-reported and unreplicated**: Anchor's 12x, 80x, and 23x; Stagehand's "2x faster, 80% more token efficient than Playwright"; Skyvern's 2.7x cheaper; Notte's 96.6% against Browser-Use's 83.3%.
- **Token-per-snapshot numbers** (200 to 400 versus 3,000 to 5,000) are third-party estimates; Microsoft publishes none. One vendor claim (PageBolt's "about 170x cheaper screenshots") is **internally inconsistent** with Anthropic's published formula and should be discarded.
- **GAIA browser-subtask rates and WorkArena headline numbers could not be verified** (leaderboards are JavaScript-rendered). Unverified.
- **OSWorld 2.0 has an irreconcilable conflict** between the paper's 20.6% and Steel's aggregator's 52 to 78%.
- **No independent, non-vendor dollars-per-task measurement** for a browser agent against a search-plus-fetch agent on the same task set was found. The closest are browser-use's $5.81 per task on hard tasks `[V]` and Gemini DR's $1 to $3 per task `[S]`, different task shapes and not comparable.
- **No authoritative global statistic exists for "percentage of websites that require JavaScript."** W3Techs' 98.9% is a usage figure, not a dependency figure; do not cite it as one. https://w3techs.com/technologies/details/cp-javascript Best dependency evidence is directional: the Vercel and MERJ analysis, Glenn Gabe's single-site case study, and HTTP Archive payload sizes (Web Almanac 2024: median 558 KB of JavaScript per mobile page, 613 KB desktop, up 14% year on year).
- **Web Almanac has no 2025 JavaScript chapter** (`/en/2025/javascript` 404s). The 2024 chapter is current.
- **Discard the content-farm tier.** A cluster of SEO and AI-generated sources ranks highly for canvas, shadow DOM, and virtualization queries (e2llm.com, isagentready.com, betterfetch.co, browserslack.com, omfang.io, accessible-data-interfaces.com, thedatagrid.com). They were avoided in favour of Google docs, Microsoft Edge docs, TanStack docs, and Playwright's issue tracker. Anyone re-running these queries will hit the same farm results.
- **JavaScript gating hit several primary dashboards**: `radar.cloudflare.com/bots`, `radar.cloudflare.com/traffic`, and DataDome's own report page all returned roughly 8 to 20 words to the scraper (DataDome's returned literally "Please enable JS and disable any ad blocker"). Those figures therefore come from press reporting and vendors' press releases, not the dashboards. Note the irony: measuring the anti-bot industry requires a browser.

## 8. What this means for the scope statement

1. **The premise holds, and there is a fourth reason it holds.** Search plus fetch owns discovery and reading, and the browser camp's own strongest voices recommend that routing. The controlled ablation (29.2% against 14.8%), the BrowseComp table, and Anthropic's and Browserbase's own docs all point the same way. The new fourth reason is permission: Cloudflare's default policy permits Search and blocks Agent, so a browser agent is in the category that gets blocked first.
2. **The durable browser advantage is narrower than the usual framing.** It is concentrated in authentication, canvas and WebGL, mutation, and interaction, and in state that lives in a cookie rather than the HTML. Public SSR listing pages fetch fine.
3. **The browser is necessary but not sufficient.** Accessibility-tree filtering, `aria-hidden`, closed shadow roots, and virtualization each exclude real content from every current agent. Structured endpoints beat the browser where they exist.
4. **jev-browser's core thesis is the industry's convergent answer.** Nearly every vendor selling LLM browser control now hands execution back to deterministic code through caching, compilation, or plan-then-deploy. Browserbase's own decision rule ("if a wrong click costs money or fails an audit, you want a script") is the scope statement's line in one sentence.
5. **The strongest competitive claim available to this effort is not speed or cost.** It is that the loop is deterministic and auditable, on work that is authenticated or stateful, at a cost per page that an LLM-per-step agent cannot match. The evidence for the cost half is that a full round here costs about $0.0012, against published browser-agent figures of 1.9¢ per simple task and $5.81 per hard task. **Correction applied:** the $0.0012 is one probe round, not a measured action-goal round. Issue 06 records it as 5 requests, 27,731 input and 3,946 output tokens at $42 per Btok with output tokens free, and the ticket that would measure the loop properly is still open. Cite it as a single probe measurement. The $5.81 per hard task is also the brief's own arithmetic on $580.87 per 100 tasks, not a published per-task figure.
